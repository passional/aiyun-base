## Context

报告分组当前的实现是全等字符串（`report/service.py:222-239`），模型串来自渠道目录原样快照（`run/model.py:61`），执行时又原样发给上游（`engine.py:271,285,332`）。参考件 `AIHUBMIX_vs_modelink_渠道性能对比报告.html` 给出了这个问题的既有答案：每个模型带 `channelNames:["claude-opus-5-5","anthropic/claude-opus-5.5"]` 与规范名 `Claude Opus 5.5`，口径说明里专列一段「模型映射」解释前缀只是渠道命名习惯。

现状盘点（本变更的起点）：

| 面 | 现状 |
| --- | --- |
| 匹配 | 字符串全等，无任何归一化/别名/映射层；全仓库零命中 |
| 导出模板 | 259 行，纯服务端 Jinja2，**零 JS**；唯一的 `<script>` 是数据转储且无人读取 |
| 现有板块 | 报告头 / 关键指标概览 / 跨渠道对比 / 交叉对比 / 异常清单 / 自动结论+备注 / 口径说明（**硬编码**） / footer |
| `params_json` | `request_count`、`warmup`(bool)、`interval_seconds`、`timeout_seconds`、`prompt`、`anomaly_threshold_seconds` |
| 参数缺口 | 热身**次数**（只有开关，固定 1 次）、**并发数**（严格串行，无此参数） |

## Goals / Non-Goals

**Goals**

- 同一个模型在不同渠道的串不同时，能落进同一行，且"落进同一行"这个判断有据可查、可追溯。
- 判断不了的时候，系统说"我判断不了"，而不是悄悄给出一个错的合并或悄悄丢掉一行。
- 导出报告达到参考件的信息架构与观感，且离线可交互。

**Non-Goals**

- 不做相似度/模糊匹配自动合并。见 D1。
- 不引入并发数参数（执行引擎是串行的，这是既有设计）。
- 不改动运行创建流程与 `channel_eval_run_combo.model` 的快照语义（仍存渠道模型串）。
- 不做原始截图存档板块（本系统数据是结构化的，没有截图数据源；参考件里那是人工内嵌的 base64）。

## Decisions

### D1 不做自动合并，改成「自动建议 + 人工确认」

**取舍**：全自动（纯归一化函数）零维护，但日期戳这类"部分重合"（`gpt-5.6-sol` vs `gpt-5.6-sol-20260115`）无法由规则判定——上游给日期戳往往是灰度/快照，也可能是不同权重。**误并比漏配更危险**：漏配至少看得见（两行），误并会让报告给出一个基于混合样本的、看起来正常的错误结论。

**决定**：自动归一化只负责把「疑似同族」连同**判断依据**列出来，管理员确认后才写库生效。

### D2 规范模型的字段

`display_name`（报告里显示的名字，必填）+ `family`（系列，可空，用于筛选）+ `status`/`remark`。不引入独立的稳定 `key`——数据库主键即稳定标识。对应参考件的 `name` / `family`。

### D3 别名全局唯一，不做平台限定

一个渠道模型串 MUST 至多属于一个规范模型。不做「同一串在不同平台归到不同规范模型」——串的语义由串自己决定（`anthropic/` 前缀本身就是渠道命名习惯），允许平台限定会造出无法向人解释的状态。

### D4 解析发生在报告渲染时，不发生在运行创建时

运行创建时快照规范模型 ID 会让历史运行在别名表变更后需要重算。渲染时解析则「补一条别名 → 历史报告立刻正确」，而导出件在导出时刻冻结 JSON，归档不受后续变更影响（既有 spec 已要求冻结）。

**代价**：Web 视图打开时报告的呈现会随后续别名维护而变。这是可接受的——它本来就是实时视图。

### D5 建议引擎的归一化规则

对每个已观测串计算归一化键：剥掉厂商/渠道前缀（首个 `/` 之前的部分）、统一分隔符（`-`/`_`/`.`/空格 → 单一分隔符）、小写化、剥掉尾部日期戳（`-20260115`、`-2026-01-15`、`@2026-01-15` 等形态）。归一化键相同的串构成一个候选组，组内出现 ≥2 个**不同原始串**时产出一条建议，依据取实际命中的差异类型：

| 依据 | 例子 |
| --- | --- |
| 渠道前缀 | `openai/gpt-6-sol` vs `gpt-6-sol` |
| 分隔符 | `claude-opus-5-5` vs `claude-opus-5.5` |
| 大小写 | `GPT-6-Sol` vs `gpt-6-sol` |
| 日期戳 | `gpt-5.6-sol-20260115` vs `gpt-5.6-sol` |

**不剥离**变体后缀（`-thinking`、`-latest` 等）——那些通常是真正不同的模型。

建议**不落库**，每次按当前已观测串实时计算；已确认的串不再出现在建议里。

### D6 未对齐模型的呈现

未对齐的串独立成组（组键就是该串本身），带 `alignment` 标记：

- `aligned`：该组由别名解析而来（或组内有基准对齐）
- `unmapped`：存在疑似同族建议但未确认
- `singleton`：无建议、本报告内只有一个组合

报告顶部给出未对齐计数提醒。**绝不隐藏、绝不与其它模型合并。**

### D7 报告视图契约变化

`ReportModelGroupSchema`：

| 字段 | 变化 |
| --- | --- |
| `model` | 语义变为「规范模型显示名」，未映射时为该渠道模型串本身。类型不变 |
| `model_key` | 新增。分组稳定键，`c{规范模型ID}` 或 `raw:{串}` |
| `raw_models` | 新增。组内出现过的渠道模型串（去重，排序） |
| `alignment` | 新增。`aligned` / `unmapped` / `singleton` |
| `family` | 新增。系列，可空 |
| `combos` / `baseline` / `has_baseline` | 不变 |

`ReportComboViewSchema.model` 保持为渠道模型串（追溯用），语义不变。

新增 `ChannelEvalReportViewSchema.alignment`（未对齐计数 + 生效映射列表）与 `.comparable_notes`（可比性提醒）。

### D8 导出模板改为客户端渲染

现有模板零 JS、服务端渲染。要交互（切基准、切指标、按系列筛选、展开样本）就得把渲染搬到客户端：数据 JSON 内嵌 + JS 重画。**代价已明确告知**：这不是"改个样式"，是渲染方式的替换。

冻结语义不变：内嵌的 JSON 在导出时刻生成，之后运行数据或别名维护都不影响已导出文件。

### D9 口径说明改为自动生成

现在是硬编码文本。改为由视图数据生成，其中**模型映射一段列出本次实际生效的映射关系**（对应参考件里手写的那段），其余口径（客户端实测定义、后台日志定义、聚合口径、成功率、基准对比、结论措辞约束、快照声明）沿用现有文本。

### D10 可比性提醒的判定项与分级

由所引用运行的 `params_json` 与执行数据求差：

| 项 | 分级 |
| --- | --- |
| 热身开关、请求模板、每组合次数、异常阈值、请求间隔、单请求超时 | 影响可比性 |
| 运行时间窗、组合数 | 提示 |

措辞限于事实（"运行 #1 开启热身、运行 #2 关闭热身"），**不含**"建议统一热身策略"这类建议性措辞——后者违反既有 spec 对自动结论的约束。

## Risks / Trade-offs

| 风险 | 缓解 |
| --- | --- |
| 别名表为空时全部模型走未对齐路径 | 与现状行为一致（每个串各自成组），存量数据无需回填；提供 `GET /model-maps/suggestions` 一次性列出建议，管理员批量确认即可 |
| 归一化建议在极端命名下产出误导性候选 | 建议必须带依据且不自动生效；管理页展示原始串与依据供人工判断 |
| 渲染时解析导致 Web 视图随后续别名维护而变 | 导出件冻结；Web 视图本就是实时视图，且这正是「补一条别名立刻修正历史报告」的收益 |
| 导出模板重写引入回归 | 保留 `report-data` JSON 内嵌约定；新增 pytest 断言导出内容包含必备板块且无外部资源引用 |
| 未对齐模型增多导致报告行数膨胀 | 顶部计数提醒 + 管理页建议列表引导确认 |

## Migration Plan

**Alembic**：新增两张表，纯新增，不改动既有表与列。

- `channel_eval_canonical_model`：`display_name`（唯一）、`family`、`status`、`remark`
- `channel_eval_model_alias`：`canonical_id`（FK，CASCADE）、`alias`（唯一）、`source`

**回滚**：downgrade 丢弃两张表，映射关系丢失，报告退回全等分组（即现状行为），无数据损坏。

**上线**：迁移后别名表为空，报告行为与现状一致；管理员从「模型对齐」页的待确认建议开始确认。
