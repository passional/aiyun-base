# 端到端验收记录：画布与交互编辑

本文件是**任务 6 的工作底稿**：由实现方准备可复现的步骤与记录模板，由用户执行并在下方回填结论。
每条任务以**用户确认**为完成标准——实现方自行跑通不算数。

回填后的去向（6.1 明写）：design.md 的 Context 里每条上游事实标注「实测确认」或「仍为文档依据」；
能力声明里被实测推翻的写法改数据（`backend/sql/image_workbench_model.json` 与库内 `capability_json`）。

## 准备

1. 后端起来：`cd backend && uv run main.py run --env=dev`（启动时自动迁移 + 导入种子）
2. 「绘图工作台 → 绘图服务」里给**火山方舟 Agent Plan** 填上真实 API Key（种子刻意不带凭证）
3. **给 pro 模型补上交互编辑的出图方式**（见下节，存量库必须做这一步）
4. 前端：`cd frontend/web && pnpm dev`，登录后进「绘图工作台」

### 为什么存量库要手动补这一步

`backend/sql/image_workbench_model.json` 里 `Seedream 5.0 pro` 已声明两种出图方式：图层拆分（参数触发）
与交互编辑（固有能力位，带标记语法）。但种子导入对**已有数据的表整体跳过**（`initialize.py:__init_data`），
因此**已建过库的环境拿不到这条新声明**——三个模型的声明里都不会有坐标标记，工作台的「打开画布」与
详情里的「在此图上继续编辑」都不会出现。

这与上一个变更的处境一致，其迁移计划给的答案也是同一个：**存量库由管理员按新种子重填，或重建库**。
迁移脚本刻意**不**代劳——「这个模型支持交互编辑」是关于上游的断言，不是结构转换，迁移不得凭空断言
（上一个变更的迁移同样拒绝凭空断言 `layer_decomposition` / `background`）。

**补法（界面，约 30 秒）**：「绘图服务」→ 选中「火山方舟 Agent Plan」→ 模型列表里编辑
`doubao-seedream-5-0-pro` → 「出图方式」区点「新增出图方式」→ 方式标识填 `interactive_edit`、
中英显示名填「交互编辑 / Interactive edit」、**「由参数触发」保持关闭**，此时会出现三个字段：

| 字段 | 填 |
| --- | --- |
| 占位形态 | `区域{n}` |
| 坐标标记写法 | `<bbox>{x1} {y1} {x2} {y2}</bbox>` |
| 坐标区间 | `1000` |

（点「新增出图方式」时这三个字段已按上面的值预填，通常只需填标识与显示名。）保存后刷新工作台即可。

**事后核对**：库里任一模型的 `capability_json.modes` 里应出现带 `marker` 的一条；工作台选中 pro 后
「打开画布」出现，切到 lite（未声明）后消失——这正是任务 5.1 的验证点。

## 6.1 核验三条上游假设（坐标标记语法 / 底图是否只剩背景 / 合成规则）

这三条**全部来自文档与官方演示，没有一条在 `/api/plan/v3` 上实测过**（design Context 末尾）。
不实测就落地的风险隔离在数据与一处代码里（D10），但结论必须回到仓库。

### (a) 坐标标记语法 `<bbox>x1 y1 x2 y2</bbox>`

最小可复现请求（ark 接入方式，参考图内联在同一请求体里）：

```bash
# 1) 先上传一张参考图，拿到它在本系统内的相对路径（前端上传或走接口）
#    POST /api/v1/image_workbench/jobs/reference-images/upload
# 2) 用带坐标标记的提示词直接打上游（把 <base_url> / <API_KEY> / <图片base64> 换成真值）
curl -sS -X POST "<base_url>/images/generations" \
  -H "Authorization: Bearer <API_KEY>" -H "Content-Type: application/json" \
  -d '{
        "model": "doubao-seedream-5-0-pro",
        "prompt": "把 <bbox>120 180 640 760</bbox> 这个区域换成一只猫",
        "image": "<图片 base64 或 URL>",
        "size": "2K",
        "watermark": false
      }'
```

**要回答的问题**：这个写法被接受吗？被改的是框住的那块区域吗？坐标是不是 0–999、空格分隔、无逗号？

- 若是：把 `backend/sql/image_workbench_model.json` 里 `interactive_edit.marker.template` 的来源
  从文档口径改成实测确认（现状为 `documented`），并在 design.md 的 Context 该条后标「实测确认」。
- 若不是：改 `marker.template`（**只改数据**），并把实际写法记进 design.md。

### (b) 底图是否只剩背景（被拆走的元素位置是否已补绘）

跑一次图层拆分（工作台勾上「图层拆分」，参考图恰好一张），下载**底图**，与最初上传的原图对比：

- 被拆走的元素（例如主体、文字）在底图里消失了吗？它原来的位置是补绘过的背景，还是一块空白/色块？
- 决定 D1 与 D2 是否成立：底图若是「只剩背景」，则「用户所见画面 = 底图 + 图层叠放」这条合成规则的前提成立。

### (c) 合成规则（图层按位置框紧裁、按 `z_index` 升序叠放）

同一次图层拆分的结果里，取某一张图层图：它的**像素尺寸**是否约等于它位置框 `absolute` 的宽高
（文档示例：图层 1273×265，绝对框 `[383,120,1655,384]` → 1272×264）？

- 是：合成规则（缩放到框、贴到 (x, y)、按层级升序）成立，`frontend/web/src/views/image_workbench/job/composition.ts` 无需改动。
- 否：把实际规则记进 design.md，并相应调整 `composition.ts`（**规则集中在这一处**）。

### (d) 第四条：底图怎么识别（已实测，且推翻了原约定）

这条原本不在 6.1 里——它写在 `CONTEXT.md`（「底图没有层级」）与 `model.is_base` 里，来源同样是
文档推断。**2026-09-17 已用真实数据核出结论，实测把原约定推翻了**：

| 任务类型 | 产物 | `z_index` | 带位置框 |
| --- | --- | --- | --- |
| 普通文生图 | 1 张 | `NULL` | 0 |
| 图层拆分 | N 张 | `0..N-1`（**无 NULL**） | N-1 |

底图是 **`z_index = 0`** 的那一张，而不是「没有这个字段」。按原判据（`z_index` 为空即底图），
图层拆分任务里 `is_base` 永远为假——后果不止画布没有画面可铺，**列表缩略图与详情里的「底图」
标记也会一起失灵**。

**已修**：`client._mark_base` 在入库边界把「没有位置框的那一张」记为底图（`z_index` 存 `NULL`），
下游一行未改；库内已存的 3 个图层拆分任务（job#39/#40/#42）也按同一规则归一了。判据用「没有
位置框」而非「`z_index` 为 0」：两者证据一致，但前者与合成规则同源，上游改成从 1 编号也仍成立。

**顺带核出（c) 的一处出入**：图层像素尺寸与位置框**不是 1:1**，同一批里逐层比值不同（约 3.8× 与
约 2.5×），但每层的宽高比与它位置框的宽高比一致——内容仍是紧裁，只是按各自分辨率回传。因此
合成**必须**按位置框缩放（`composition.ts` 一直是这么做的），这条比原先以为的更要紧。**画面的
观感对不对需要你在 6.2 第 3 步用眼睛确认**。

**结论回填**

| 假设 | 结论（实测确认 / 仍为文档依据 / 被推翻，附实际写法） | 回填位置 |
| --- | --- | --- |
| (a) 坐标标记语法 | | design.md Context；按需改种子 `marker.template` |
| (b) 底图只剩背景 | | design.md Context |
| (c) 合成规则 | 紧裁：**实测确认至内容**；1:1 的猜想**被推翻**（逐层分辨率不同，必须缩放） | design.md Context |
| (d) 底图怎么识别 | **被推翻并已修**：上游给底图 `z_index = 0`，我们在入库边界记为「无层级」 | design.md Context；`client._mark_base` |

## 6.2「拆 → 改」闭环

1. 工作台上传一张参考图，**打开画布 → 用这张画面生成**（画布把参考图作为本次参考图）
2. 勾上「图层拆分」提交；等任务成功，产物里应有底图 + 若干图层
3. 打开该任务的**详情** → 点「在此图上继续编辑」：
   - 画布应显示**底图 + 各图层按层级叠放的合成画面**，且与详情里的产物列表一致
   - 点选其中一个图层 → 它的位置框被高亮，提示词里出现「区域 N」
   - 把「区域 N」放到句子里你想要的位置（例如「把区域1换成一只猫」）
4. 点「用这张画面生成」→ 关闭画布 → 提交
5. 确认：
   - [ ] 新任务详情的**选区来源**列出了「区域 1（取自图层 #N）」
   - [ ] 详情的原话含「区域1」，最终提示词含 `<bbox>…</bbox>`
   - [ ] 回到**上一次拆分**的任务详情，删除它 → **被拒绝**，且答复里列出了引用它的任务（新任务的编号）
   - [ ] 该次拆分的**全部**产物（底图 + 每一张图层）都无法单独删除，而不是只有被点选的那一张

## 6.3 坐标不丢失

两种提交都必须被拒绝，且提示要指出是**哪一个**选区：

- [ ] 提示词里引用了「区域2」，但只给了区域1 的坐标 → 拒绝，提示里出现 `#2` 与「没有对应的坐标」
