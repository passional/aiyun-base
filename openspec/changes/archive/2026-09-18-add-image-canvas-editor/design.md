## Context

动机见 `proposal.md`。此处只列影响方案的现存事实与约束。

**依赖**：本变更建立在 `add-image-model-capability` 之上——清单结构、产物表、清单驱动的参数面都由它引入。两者都实现完才能验收。

**起点**：提交契约（变更一之后）是 `{model_pk, prompt, params, reference_images}`；任务表有 `prompt` 但没有「最终提示词」；产物在 `image_workbench_artifact`（`z_index` 为空表示底图，带位置框与文件路径）；删除任务时逐张真删产物（`job/service.py:359` 一带）；参考图上传接口 `POST /jobs/reference-images/upload` 已存在，前端可复用。

**上游事实（本次查证所得，逐条带出处）**

- **底图只剩背景**，被拆走元素的位置是**补绘**过的。所以「用户所见的画面」= 底图 + 各图层按层级叠放，合成绕不开。证据：字节 Seed 官方博客「被主体遮挡的背景区域也被补全还原」；官方演示视频逐帧可见中央画布无主体无文字；Ark 文档自身的合成指引要求把图层放到输出底图上；ComfyUI 官方合作节点称其为 "an inpainted background plate"。
- **底图由「没有位置框」识别，上游给它的编号是 0**（**实测确认**，2026-09-17 在 `/api/plan/v3` 上核验）。图层拆分时上游给**每一张**都编了 `z_index`——底图 `0`、图层 `1..N`，与普通文生图「不给 `z_index`」不同。底图是**唯一没有位置框也没有名称**的那一张，且尺寸最大。原先按文档推断的「底图 = `z_index` 为空」因此在真实响应上**永远不成立**（后果不止画布没有画面，列表缩略图与详情里的「底图」标记会一起失灵）。处理：在**入库边界**翻译成我们的表示——`client._mark_base` 把没有位置框的那一张记为 `z_index` 为空，「底图没有层级」（CONTEXT.md）继续成立，下游不必认识两套约定。判据取「没有位置框」而不是「`z_index` 为 0」：证据上两者一致，但前者与合成规则同源，上游改成从 1 编号也仍成立。
- **图层按各自的位置框紧裁**（**实测确认至内容，分辨率另有出入**）。文档示例里图层尺寸 `1273x265`，其绝对框 `[383,120,1655,384]` → 1272×264，看起来是 1:1；实测中**并非 1:1**：图层像素尺寸/位置框的比值逐层不同（同一批里一层约 3.8×、另一层约 2.5×），说明上游把紧裁结果按各自的分辨率回传。内容仍是紧裁（每层的宽高比与它位置框的宽高比一致），所以**合成时必须按位置框缩放，不能原尺寸粘贴**——这条比原先以为的更要紧。
- **合成规则**：把图层缩放至其宽高、放到输出底图的 `(x, y)`，多个图层按 `z_index` 从小到大依次叠放。
- **底图分辨率与 `size` 一致、宽高比与输入一致，且恒无 alpha**（即使 `output_format` 为 `png`）；图层恒为 PNG 且带 alpha。
- **坐标标记**：`<bbox>x1 y1 x2 y2</bbox>`，坐标归一化到 1000×1000、取值 0–999、空格分隔且无逗号，一段提示词里可以出现多个。
- **交互编辑在上游没有对应参数**，只有提示词约定，因此不可能从参数值派生。

**约束**：上述上游事实里，**没有任何一条在 `/api/plan/v3` 上实测过**——没有任何一页文档把 `layer_decomposition` 与这个 base_url 同时写出。按变更一的取向，可变的写法进清单、可变的规则集中在一处，把未实测的风险隔离在数据与一处代码里。

## Goals / Non-Goals

**Goals:**

- 让「拆 → 改」成为闭环：图层拆分产出的图层可以被选中、被再次提交为输入。
- **发出去的等于用户看到的**——由构造保证，而不是靠约定。
- **坐标不静默丢失**：提示词引用的选区拿不到坐标时，拒绝提交。

**Non-Goals（设计层面）:**

- 不做 Seedream 5.0 lite / 4.5 / 4.0 的「在参考图上画记号」交互（两套交互不是一套；本次只做 pro 的坐标标记）。
- 不做 `<point>` 点标记，只做 `<bbox>` 范围标记。
- 不做服务端合成（见 D1）。
- 不做产物的版本树或编辑谱系可视化——只记录来源引用与反向可查。
- 不在画布上做图层的增删与重排，只做选择与编辑。

## Decisions

### D1 合成在前端做，合成图走既有参考图上传接口

画布本来就要渲染合成结果，导出几乎是免费的：画布 → 导出 PNG → 走 `POST /jobs/reference-images/upload` → 得到文件路径 → 作为本次提交的参考图。

**理由**：坐标系**自洽**——合成图是用同一批位置框拼出来的，框必然落在该图层上。「发出去的就是看到的」由构造保证。

**考虑过的替代**

- **提交那次图层拆分任务的原始参考图**：省掉合成代码，且像素上忠于用户当初的上传。但它依赖一个没有文档支持的假设——「模型重绘时没有移动任何元素」。位置框是在**重绘后的底图**上算出来的，套回原图若对不齐，编辑会落在错误的位置，而且**看不出来**。相比之下前端合成若失效，表现是成品与用户原图有可见差别——看得见，能发现。**拒绝。**
- **后端合成**：可信、可重放，但要引入图像处理库（后端目前没有），且必须保证前后端渲染一致（层序、alpha 处理），一致性维护成本高于它换来的那点可信度。**拒绝。**

### D2 合成严格按 `z_index` 升序，不假设「底图一定在最底」

底图（`z_index` 为空）先铺底，各图层按 `z_index` 升序依次叠放。**不做**「底图在最底所以可以短路」这类优化：上游把背景本身也可能拆成图层，一旦某层是整画布不透明的，只有严格的层级顺序是对的。

### D3 选区是结构化输入，服务端渲染最终提示词

```
POST /image_workbench/jobs/create       权限 image_workbench:job:create
{
  "model_pk": 1,
  "prompt": "把区域1换成一只猫，背景区域2调亮",
  "params": { … },
  "reference_images": ["…合成图的路径…"],
  "composition_source_job_id": 7,                 // 构成这张参考图的那次生成（画面来源）
  "selections": [
    { "index": 1, "artifact_id": 8 },               // 点选图层：坐标由服务端读该产物的位置框
    { "index": 2, "bbox": [120, 180, 640, 760] }    // 自行划框：坐标由前端给出
  ]
}
```

**画面来源与选区来源是两件事，不能合并：**

- `composition_source_job_id` 回答「这张参考图是由哪些产物拼出来的」。合成图用到底图与**全部**图层，所以这里提交的是**产出这些产物的那次绘图任务**，由服务端展开成该任务的全部产物并逐一记为来源。
- `selections[].artifact_id` 回答「这一个选区取自哪一层」。它只在点选图层时才有；用户自行划框时没有。

**为什么画面来源提交任务标识而不是产物清单**：若让前端列产物，服务端就只能校验「它们同属一个任务」这一条，**列得全不全无从校验**——而「记全」正是这条修复要保证的事。改成提交任务标识后，产物集合由服务端自己展开，「全部」是**构造出来的**而不是前端声明的，也就不需要一条无法执行的完整性要求。顺带，「属于同一画面」的校验也随之消失：同一个任务标识意味着同一画面，这条错误不可能发生。

两者都写入引用关系（D6）、都受删除保护（D7）。画布显示的不是产物（例如用户直接上传的一张参考图）时，该字段缺省。

服务端把 `artifact_id` 解析成该产物的**归一化位置框**（0–999），与前端给出的 `bbox` 一起构成选区集合，再渲染最终提示词。

**理由**：坐标属于结构化数据，不属于自然语言——写成结构化字段后可以校验（区间、非零面积、序号唯一），也不会被用户在文本框里手改坏。而「画面来源」与「选区来源」回答的是两个不同的问题：合并成一个字段，必然有一边记不全。

### D4 占位符由前端插入，服务端按能力声明替换

能力声明里每一种出图方式声明自己的占位形态与标记写法：

```jsonc
{ "key": "interactive_edit", "trigger": null,
  "marker": { "placeholder": "区域{n}", "template": "<bbox>{x1} {y1} {x2} {y2}</bbox>", "range": 1000 } }
```

`range` 是坐标空间的大小：合法坐标是 `0 .. range-1` 的整数。规格要求「坐标超出**能力声明规定的区间**」被拒绝，代码就不该自己记一个数字——上游把坐标归一化到 1000×1000、取值 0–999，那个 1000 因此落在声明里。`trigger` 为 null 的方式**必须**声明 `marker`：不由参数触发的方式就是靠坐标表达位置的那一类，占位形态与标记写法是它与上游的全部约定；触发式的方式（图层拆分）与坐标无关，不要求也不禁止。

前端在光标处插入 `区域1`、`区域2`……用户在句子里自己决定位置该出现在哪；服务端按声明的占位形态识别并替换成填好坐标的标记。

**理由**：**标记在句中的位置本身就是语义**——文档示例是「把图 1 `<bbox>…</bbox>` **区域**换成花园」，被替换的是那个区域。服务端只能把标记追加在句首或句尾，而「追加在句首/句尾」没有任何文档支持，等于赌。让用户决定位置、让系统决定写法，各做各擅长的。

**两条硬规则**（都写进了规格）：

- 提示词引用了选区、但对不上任何坐标 → **拒绝提交**并指出是哪一个，不静默丢弃。
- 有选区、但提示词里没有任何引用 → 同样拒绝：这个坐标白给了，提交出去只会让人以为生效了。

### D5 提示词两个形态，新增 `prompt_final` 列

`prompt` 存用户原话（含占位符），`prompt_final` 存实际发给上游的文本（含坐标标记）。两者相同时前端只呈现一份。

**理由**：与仓库既有的取向一致——`params_json`、`model_id` 都是**快照**而非按需重算。若只存原话，将来标记写法一变，重建出的文本就不等于当时真正发出去的那段。

### D6 引用关系用关联表，不用 JSON 列

```
image_workbench_job_artifact_ref
  id / job_id / artifact_id / 公共审计列
  UNIQUE(job_id, artifact_id)
  INDEX(artifact_id)
```

**两类引用写进同一张表**：画面来源（D3 的 `composition_sources`）与选区来源（`selections[].artifact_id`）。从删除保护的角度看它们没有区别——都是「这张产物被谁用过」，因此不需要两张表，也不需要给引用标类型。

**理由**：删除保护是**热路径**——每次删任务都要问「我的产物有没有被别人引用」。反向查询（按 artifact_id 找引用它的任务）放 JSON 列虽省一张表，但只能全表扫。索引一次解决。

### D7 删除保护：拒绝，并指出引用者

删除任务前先收集该任务的全部产物，查关联表看是否有**其它任务**引用；有则拒绝，并列出引用它们的任务。引用包含两类（画面来源与选区来源，见 D6），对删除保护一视同仁。不级联删除、不标记「输入已失效」（两条都被 `docs/adr/0007` 拒绝）。

**代价**：产物几乎不可删——一次图层拆分产出十几张产物，用户每改一轮就多一批引用节点。这是 ADR-0007 明文记录的、刻意接受的代价。

**而画面来源会把代价整批放大**：只要用户编辑过某次生成中的**任意一个**图层，那次生成的**全部产物**（底图 + 全部图层）就都进了引用关系，整个任务从此不可删。这正是 D3 选择提交**任务标识**而非产物清单的直接后果——产物集合由服务端展开，「整批」是构造出来的，可追溯性因此不出现缺口。代价是刻意的：半记录的画面来源会让一部分产物仍可被删，删掉之后「来源可反查」就成了半真半假的陈述。

### D8 画布入口由能力声明决定

清单的 `modes` 里存在 `interactive_edit`（`trigger` 为 `null`，见变更一 D1 的补丁）时，前端才提供画布入口。出图方式**不单独提交**——延续变更一 D3：提交契约里没有 `mode` 字段，用户不选它，前端按当前模型的能力决定给不给画布。

### D9 API 契约变更一览

| 端点 | 权限 | 变更 |
|---|---|---|
| `POST /image_workbench/jobs/create` | `image_workbench:job:create` | 请求增加可选的 `selections`；不传时行为与变更一一致 |
| `GET /image_workbench/jobs/detail/{id}` | `image_workbench:job:query` | 响应增加 `prompt_final` 与 `selections`（含来源产物标识） |
| `GET /image_workbench/jobs/models/optionselect` | `image_workbench:job:query` | 声明中增加交互编辑的出图方式与标记语法 |
| `POST /image_workbench/jobs/reference-images/upload` | `image_workbench:job:create` | 不变——合成图走同一条路 |

不新增权限码、不新增菜单。

### D10 未实测假设的隔离

本变更依赖的上游行为（标记语法、底图语义、合成规则）**全部来自文档与官方演示，没有一条在 `/api/plan/v3` 上实测过**。隔离方式：标记语法放在能力声明里（数据），合成规则集中在前端的一个函数里。实测若推翻其中任何一条，改动限于清单数据与那一个函数，不触及提交契约、数据模型与规格。

### D11 重试复用最终提示词快照，不重新渲染

重试以原任务的**最终提示词**、参数快照、选区快照与来源引用重新提交；原话原文只用于展示，不参与重试。

**为什么不是「重新渲染」**：重试的语义是「把当初那次请求再发一次」，而当初真正发出去的就是 `prompt_final`。若改成拿原话按当前声明重渲染，标记写法一旦被改过，重试发出去的就不再是当初那次请求了——而这正是 D5 要保留 `prompt_final` 快照要防的事。

**为什么必须显式规定**：既有的重试实现（`job/service.py:325`）只取 `job.prompt` 与参数里的少数字段重新提交。含选区的任务照此重试，只会发出**仍带 `区域1` 占位符、却没有任何坐标**的原话——轻则被新校验拒掉（用户看到一个「重试不了」的失败任务），重则把未渲染的提示词发到了上游。

## Risks / Trade-offs

- **[坐标标记语法未实测]** → 语法进能力声明。若实测发现写法不同，改数据即可，不动代码。
- **[底图语义的依据是官方演示与第三方实现，不是 API 文档明文]** → 合成规则集中在一处；验收里有一条与实测结果对照的任务。
- **[合成图是模型重绘结果的拼合，与用户原图有细微差别]** → 这是 D1 里刻意选择的失效模式（看得见的偏差优于看不见的错位）。界面 MUST 在画布旁说明这是拆分结果的重绘画面。
- **[用户把占位符改坏]** → 提交时拒绝并指出是哪一个选区；绝不静默丢弃坐标。
- **[产物几乎不可删]** → ADR-0007 已记录该代价；删除被拒时界面要列出引用它的任务，让用户知道去删什么。
- **[删除任务多了一次反向查询]** → 关联表 + `artifact_id` 索引。

## Migration Plan

**Alembic 迁移（一次）**

1. `image_workbench_job` 增加 `prompt_final`，历史行回填为 `prompt` 的当前值（它们本来就没有坐标标记，回填值等于真实发出的文本）。
2. `image_workbench_job` 增加 `selections_json`，存储本任务的选区快照（含来源产物标识）。快照而非引用——与 `params_json` 同一取向。
3. 新建 `image_workbench_job_artifact_ref` 表。历史行无来源引用，不需要回填。

**回滚是有损的。** `downgrade -1` 删除 `prompt_final`、选区快照与引用关联表之后：

- **带选区任务的最终提示词无法重建**。这类任务的 `prompt` 里只剩 `区域1` 这样的占位符，选区一旦丢失，占位符就无从解释；参数快照里也没有坐标。**这正是 D5 要保留 `prompt_final` 快照的理由**——快照存在的意义就是它不可重建，删掉它当然是有损失的。先前写成「无数据损失」是错的。
- **选区本身丢失**，连带该任务与来源产物的引用关系一并消失，删除保护随之**静默失效**：被引用的产物在回滚后可以被删掉，而且不会有人提示。

因此回滚有两个前置条件，写进操作步骤而不是靠记性：**先确认库中不存在带选区的任务，或先把这些任务的原话、最终提示词、选区快照与来源引用导出留存**。库里没有带选区的任务时，回滚才是无损的。

**回滚不静默**：迁移在删除前先数一遍带坐标标记的任务行，有则打一条警告，写明「这些任务的最终提示词与选区快照将丢失且无法重建，删除保护随之失效」。两条前置条件靠人记住，这条警告靠运行时说出——记性会失灵，日志不会。

**存量库还要补一份能力声明。** 交互编辑是**声明**出来的，而种子导入对已有数据的表整体跳过
（`initialize.py:__init_data`），因此已建过库的环境不会自动获得这条新出图方式——工作台的画布入口
与「在此图上继续编辑」都不会出现。迁移刻意不代劳：「这个模型支持交互编辑」是关于上游的断言，不是
结构转换，与变更一的迁移拒绝凭空断言 `layer_decomposition` / `background` 是同一条理由。存量库由
管理员按新种子重填（界面里新增一条固有出图方式），或重建库；具体步骤见 `acceptance.md`。

**兼容性**：不传 `selections` 的提交与变更一完全一致。前端未升级时后端仍能正常工作。
