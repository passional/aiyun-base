# 出图参数面由能力声明驱动，不用具名参数与硬编码表单

Status: accepted

基座（变更 `add-image-workbench`，已归档）里的 `capability_json` 只声明**选项集**：可选尺寸、是否支持参考图与张数上限、输出格式、水印默认值。前端用它取选项，但表单的五个控件是手写的（`views/image_workbench/job/index.vue` 的 `generateFormItems`）；后端提交接口是具名字段（`size` / `output_format` / `watermark` / `reference_images`）；上游请求体由 `job/client.py` 显式拼装。三者各自为政。

要补的是六个参数（`optimize_prompt_options.mode`、`background`、`response_format`、水印开关、扩展的 `size`）加图层拆分与交互编辑。已知的跨模型差异已经很多：`layer_decomposition` 与 `background` 仅 5.0 pro 有，`optimize_prompt_options.fast` 不支持 lite，`size` 的档位是 pro `1K/1.5K/2K`、lite `2K/3K/4K`，`max_reference_images` 是 pro 10、lite 14，而同一个 `size` 在图层拆分方式下取值域与默认值又不同。这些不是「多写几个控件」的量，是**模型 × 参数 × 出图方式**的三维网格，手写不收敛。

**决定：把能力声明从「选项集」升级为驱动参数面的清单。** 清单逐模型声明每个参数的 key、显示名、控件类型、取值域、默认值、来源标记，以及条件依赖；条件依赖用三种固定形态的结构化字段表达（参数间依赖、请求状态依赖、绘图模型的出图方式位），不做通用表达式。前端按清单渲染表单，后端按清单校验并组装上游请求体；绘图任务的提交接口改为接受开放的参数字典，不再是具名字段。

理由：参数面的全部知识（取值范围、默认值、何时可用）本就该集中在一处。放在能力声明里，加模型与加参数是改数据；放在代码里，是前后端各改一遍。「条件依赖用固定形态而非表达式」是刻意的：DSL 是一套小型语言的全部代价（词法、求值、错误处理，且前后端各一份求值器要保证行为一致），而今天已知的全部规则都能被三种形态表达；真出现第四种形态时是从固定形态长出 DSL，不是返工。

**后果（须记住）**：上游请求体的类型安全变弱——值域校验从 Pydantic 字段类型转移到清单数据，清单写错的表现是运行期上游报错而不是提交前的表单报错。因此清单本身需要一份存储时的结构校验，且清单是**数据**，可以逐模型不同。水印（见 ADR-0008）与出图方式同样由这份清单驱动，不再有特例。

**Considered Options**

- 继续具名字段 + 硬编码表单：每加一个参数或一个模型都要改前后端两处，且参数的联动散落各处——放弃。
- 通用表达式 DSL：今天四条规则用固定形态即可表达，为未知的第五种规则先写一套求值器——放弃（升级路径存在，但不是现在）。
- 只把参数值挪进能力声明、仍用具名字段：是介于两者之间的折中，但具名字段无法表达「参数之间的联动」，而联动正是这次的主要成本——放弃。
