# ASR 同步执行：逐文件请求、每用户串行、单文件默认 5 分钟

Status: accepted

工作台需要支持批量选择音频（最多 10 个），而识别接口采用同步等待。部署的 nginx 对代理请求设置 `proxy_read_timeout 300s`；官方示例按实时节奏发送音频分片（每 200ms 一片），10 分钟音频仅发送就需 600s，必然被网关中断。

**决定：同步执行，逐文件请求。** 前端把批量文件排成队列，逐个调用同步识别接口；每个文件独立成败，失败项可单独重试。后端分片不按实时节奏发送，而是尽快发完（保留可调的小间隔），单文件默认上限 5 分钟、20MB，限额按模型可配。同一用户同时只允许一个识别请求在途（Redis 占位），不同用户互不影响。转写任务落库，原音频不落盘。

理由：同步接口实现简单，与「上传后立即看到结果」的交互一致；逐文件顺序调用让批量与「每用户串行」天然兼容，无需后台任务状态机。5 分钟上限按 300s 网关反推，给上游处理留出余量。

**后果（须记住）**：超过默认上限的音频会被直接拒绝。管理员可调低限额，但调高前必须先确认上游处理耗时与网关超时；若实测表明上游要求按实时节奏接收分片，本决定失效，需要改异步任务或调整网关超时，不能只调大 `max_duration_sec`。批量 10 个 5 分钟文件是顺序执行，总耗时可观，界面必须逐行显示进度而不是整批转圈。

**Considered Options**

- 保留 10 分钟并调大 nginx 超时到 900s：部署变更会影响所有接口，且不解决「官方示例按实时节奏发送」的根本问题——放弃。
- 异步任务 + 轮询：可处理长音频与断线恢复，但要引入任务状态机、后台执行器与进度通道，首版过重——放弃。
- 多文件打包成一个请求：请求时长随文件数线性增长，更易超时，且部分失败无法独立表达——放弃。
