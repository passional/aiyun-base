# 绘图服务不复用「平台」，建为平级独立实体

Status: accepted

图片生成需要一处管理员可配的上游凭证（base_url + key + 模型 ID）。系统里已经有一个带 base_url 和凭证的实体——渠道评估的「平台」（`channel_eval_platform`），且它已经配好了 apiworld。直觉做法是复用：给平台加个「可作绘图用」的标记，图片请求走同一份凭证。

**决定：不复用。** 新增与「平台」**平级**的独立实体「绘图服务」，不引用平台、不继承渠道与「指定渠道」的概念。管理员在后台分别配置两个绘图服务：火山方舟 Agent Plan（接入方式「火山方舟」，base_url `https://ark.cn-beijing.volces.com/api/plan/v3`，挂 pro / lite 两个绘图模型）与 apiworld（接入方式「OpenAI 兼容」）。绘图服务下分两级：服务持有名称、接入方式、base_url、凭证；模型持有模型 ID 与能力声明。

理由：`平台` 的定义里绑着 new-api 管理接口的假设——管理员的 `admin_key` 与 `admin_user_id`、运行时经管理接口实时拉取渠道目录（ADR-0003）、以及借管理员令牌实现的渠道 pin（ADR-0001）。绘图服务只需要一个调用端点，把这些假设一起继承过来，会让一个只需要 base_url 的配置项背上三样它用不到的东西。而火山方舟根本不是 new-api 的渠道，用「渠道」指代它两头都不准。

**后果（须记住）**：管理员手填凭证意味着 apiworld 的 key 会在平台上存两份——评估平台一份、绘图服务一份。这与 ADR-0003「避免业务侧再配一遍、防漂移」的立场有张力，是本次刻意接受的代价。将来若要消除，做法是给绘图服务加一个可选的「引用已有平台」开关，而不是把两个实体合并。

**Considered Options**

- 把绘图服务做成「平台」的一种（加标记位）：要用绘图功能的平台就必须背上评估用的管理员令牌字段；且火山的 `type` 无处安放——放弃。
- 复用「渠道」术语、强制每个绘图服务 pin 到一个渠道：火山没有 new-api 渠道可 pin；且会丢掉"平台整体负载均衡"的场景——放弃。
- 绘图服务引用平台的凭证（而非复制）：绕开了重复配置，但把绘图功能的可用性绑死在评估平台的配置上；评估平台被停用或改动时会连带失效——放弃。
